Latent Coverage Cartographer

Maps the blind spots of any RAG system before users find them. Generates synthetic probe queries, scores retrieval coverage, clusters failures into dark zones, and produces a structured gap report with document recommendations.

01

Thesis & problem

Every RAG system has a coverage boundary — a frontier beyond which it can no longer answer reliably. Inside the boundary: good retrieval, grounded answers. Outside it: the system retrieves tangentially related chunks, generates confidently-phrased hallucinations, and neither the system nor the user has any way to know.

The core problem

RAG systems don't fail loudly at coverage boundaries. They don't say "I don't have information about this." They say "Based on the available context..." and then hallucinate fluently. The failure mode is invisible — to the user, to the developer, and to any standard RAG evaluation metric that only measures answer quality on queries the system can handle.

Three types of coverage failure

TypeWhat it looks likeWhy it's hard to detect
Absolute gapTopic X has zero documents in the KB. Any query about X retrieves irrelevant chunks.System returns confident-sounding answers from tangentially related documents.
Thin coverageOne document covers topic X, but it's a 2-sentence mention in a larger document. Queries need more depth than exists.Retrieval succeeds (document is found) but the answer is incomplete. Hard to distinguish from adequate coverage.
Stale coverageDocuments exist but are outdated. Retrieval finds them, answers are confidently wrong.Covered by the Knowledge Decay Monitor (Project 16), not the Cartographer. Out of scope here.

Why existing tools don't solve this

RAGAS, TruLens, and DeepEval all evaluate RAG quality on queries you provide. They tell you how well the system answers the queries it's given. None of them tell you what queries the system can't answer — because generating those queries requires exploring the space of possible questions, not just scoring answers to known ones. The Cartographer is the first tool to treat coverage mapping as an exploration problem rather than an evaluation problem.

02

System architecture

Five sequential stages. Each stage has a clear contract with the next. The output of Stage 5 is a structured gap report consumed by the developer or platform team.

Stage 1: Probe Query Generator
  Input:  Knowledge base (documents/chunks)
  Output: N synthetic probe queries (5,000–50,000 depending on KB size)

Stage 2: Coverage Scorer
  Input:  Probe queries + RAG system under test
  Output: (query, coverage_score, retrieval_evidence) for each probe

Stage 3: UMAP Projector
  Input:  Query embeddings for all probes
  Output: 2D coordinates for each probe query

Stage 4: HDBSCAN Clusterer
  Input:  2D UMAP coordinates
  Output: Cluster assignments + noise labels

Stage 5: Gap Analyzer & Report Generator
  Input:  Cluster assignments + coverage scores
  Output: Structured GapReport with dark zones, recommendations, priority scores
Design principle: RAG-agnostic

The Cartographer never calls the RAG system's internal components directly. It only calls the public query interface — the same API your users call. This makes it compatible with any RAG system: Qdrant-based, Pinecone-based, LlamaIndex, LangChain, custom. You point it at a URL and it works.

03

Synthetic probe query generation

This is where the Cartographer's intellectual depth lies. Generating probe queries that genuinely test coverage requires four distinct generation strategies running in parallel. Using only one strategy produces a biased probe set that misses entire categories of gaps.

Strategy 1: Taxonomy-guided generation (covers the KB)

async def taxonomy_guided_generation(kb_chunks: List[str], n: int = 2000) -> List[str]:
    # Step 1: Extract topic taxonomy from KB using BERTopic
    topic_model = BERTopic(embedding_model="all-MiniLM-L6-v2", nr_topics=50)
    topics, probs = topic_model.fit_transform(kb_chunks)
    topic_info = topic_model.get_topic_info()

    # Step 2: Generate N/topics queries per topic cluster
    queries = []
    for topic_id, topic_keywords in topic_info.iterrows():
        prompt = f"""
Generate 5 factual questions that test knowledge of: {topic_keywords['Name']}
These questions should be answerable from a knowledge base on this topic.
Return only the questions, one per line. No numbering, no explanation.
Vary: factual lookup, comparison, causal, procedural, definitional.
"""
        result = await claude_haiku.ainvoke(prompt)
        queries.extend(result.strip().split("\n"))
    return queries

Strategy 2: HyDE-based adversarial generation (probes the boundary)

HyDE (Hypothetical Document Embeddings) is normally used to improve retrieval. Here it's inverted: generate hypothetical documents about topics that should be in the KB but might not be, then generate queries against those hypothetical documents. This probes the frontier of coverage.

async def adversarial_boundary_generation(kb_chunks: List[str], n: int = 1000) -> List[str]:
    # Generate "adjacent topic" documents — related to KB content but not in it
    sample_chunks = random.sample(kb_chunks, min(100, len(kb_chunks)))
    adjacent_topics_prompt = f"""
Given these document excerpts from a knowledge base:
{chr(10).join(sample_chunks[:10])}

Generate 20 related topics that are NOT covered by these excerpts but are
closely adjacent to them. These are the "boundary topics" — things a user
might naturally ask about after reading this content.

Return only topic names, one per line.
"""
    adjacent_topics = await claude_haiku.ainvoke(adjacent_topics_prompt)

    # For each adjacent topic, generate probe queries
    queries = []
    for topic in adjacent_topics.strip().split("\n"):
        probe_prompt = f"Generate 3 specific questions about: {topic}"
        result = await claude_haiku.ainvoke(probe_prompt)
        queries.extend(result.strip().split("\n"))
    return queries

Strategy 3: Counterfactual generation (probes reasoning gaps)

Takes existing KB chunks and generates queries that seem answerable from the KB but actually require information not present. Tests whether the system hallucinates or correctly expresses uncertainty.

async def counterfactual_generation(kb_chunks: List[str], n: int = 500) -> List[str]:
    # For each sampled chunk, generate queries that require ONE piece of
    # information not in the chunk — tests hallucination on near-misses
    queries = []
    for chunk in random.sample(kb_chunks, n):
        prompt = f"""
Given this document excerpt:
"{chunk}"

Generate 2 questions that seem related to this content but require
information NOT contained in it to answer correctly.
The questions should be specific and factual.
Return only the questions, one per line.
"""
        result = await claude_haiku.ainvoke(prompt)
        queries.extend(result.strip().split("\n"))
    return queries

Strategy 4: User pattern simulation (probes real-world gaps)

If you have query logs from your RAG system, cluster them and identify query patterns that cluster near high-hallucination responses. Generate synthetic variants of those patterns to stress-test the coverage around known weak spots.

async def user_pattern_simulation(query_logs: List[str], n: int = 500) -> List[str]:
    # Cluster historical queries, identify clusters with high hallucination rate
    embeddings = embed_batch(query_logs)
    clusters = hdbscan_cluster(embeddings)
    high_hallucination_clusters = [
        c for c in clusters
        if c.avg_hallucination_score > 0.6
    ]
    # Generate synthetic variants around problematic clusters
    return await generate_cluster_variants(high_hallucination_clusters, n)

04

Coverage scoring formula

For each probe query, a coverage score is computed from three independent signals. The score represents "how well can this RAG system answer this type of question?" — not whether any specific answer is correct.

Coverage Score — composite of three retrieval signals
CS(q, KB) = α·RC(q,KB) + β·(1 − SE(q,KB)) + γ·(1 − HP(q,KB))

where:
RC = Retrieval Confidence (max cosine similarity of top-k chunks to query)
SE = Semantic Entropy (entropy of retrieved chunk embedding distribution)
HP = Hallucination Probability (cross-encoder relevance gap score)

Default weights: α=0.4, β=0.35, γ=0.25 (tunable per deployment)

Signal 1: Retrieval Confidence (RC)

The maximum cosine similarity between the query embedding and the top-k retrieved chunk embeddings. High RC = the system found highly relevant chunks. Low RC = the system retrieved tangentially related content — coverage failure signal.

def retrieval_confidence(query: str, retrieved_chunks: List[str]) -> float:
    query_emb = embed(query)
    chunk_embs = [embed(c) for c in retrieved_chunks]
    similarities = [cosine_similarity(query_emb, ce) for ce in chunk_embs]
    return max(similarities) if similarities else 0.0

Signal 2: Semantic Entropy (SE)

The Shannon entropy of the retrieved chunk embedding distribution. Low entropy = all retrieved chunks are semantically similar to each other (focused, relevant retrieval). High entropy = retrieved chunks are semantically diverse (the system is grasping at unrelated content — coverage failure signal).

from scipy.spatial.distance import pdist
from scipy.stats import entropy

def semantic_entropy(retrieved_chunks: List[str]) -> float:
    if len(retrieved_chunks) < 2: return 0.0
    chunk_embs = np.array([embed(c) for c in retrieved_chunks])
    # Pairwise cosine distances → histogram → entropy
    distances = pdist(chunk_embs, metric="cosine")
    hist, _ = np.histogram(distances, bins=10, density=True)
    hist = hist + 1e-10  # numerical stability
    return float(entropy(hist / hist.sum()))

Signal 3: Hallucination Probability (HP)

Uses a cross-encoder relevance model to score how well the retrieved chunks actually answer the query. Low cross-encoder score despite high cosine similarity = the chunks are topically similar but don't contain the answer — a strong hallucination precursor signal.

from sentence_transformers import CrossEncoder

cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def hallucination_probability(query: str, retrieved_chunks: List[str]) -> float:
    # Score each (query, chunk) pair with cross-encoder
    pairs = [(query, chunk) for chunk in retrieved_chunks]
    scores = cross_encoder.predict(pairs)
    max_relevance = float(np.max(scores))
    # Normalize to [0,1]: high relevance = low hallucination probability
    # Cross-encoder outputs raw logits, sigmoid to normalize
    normalized = 1 / (1 + np.exp(-max_relevance))
    return 1.0 - float(normalized)  # invert: high relevance → low HP
Why three signals instead of one

RC alone misses thin coverage (chunks retrieved with high similarity but insufficient depth). SE alone misses narrow gaps (a single off-topic chunk retrieved with high similarity). HP alone is expensive to compute at scale. The composite CS uses the cheaper RC and SE signals as a fast filter, and HP only on the borderline cases (CS between 0.35 and 0.65) where the additional signal cost is justified.

UMAP + HDBSCAN clustering

With 5,000–50,000 probe queries scored, raw scores are not enough — we need to identify which topic clusters have coverage failures, not just which individual queries fail. UMAP reduces query embeddings to 2D for visualization; HDBSCAN identifies semantic clusters; coverage scores are aggregated per cluster.

UMAP configuration

import umap
import numpy as np

def project_to_2d(query_embeddings: np.ndarray) -> np.ndarray:
    reducer = umap.UMAP(
        n_neighbors=15,       # local neighborhood size — 15 is standard for 5k-50k points
        min_dist=0.1,         # minimum distance between points in 2D
        n_components=2,       # 2D for visualization; use 10D for HDBSCAN input
        metric="cosine",      # cosine distance for sentence embeddings
        random_state=42,      # reproducibility
        low_memory=False,     # use fast approximate nearest neighbors for speed
        n_epochs=200,         # more epochs = better layout, slower
        spread=1.0,           # scale of embedding in output space
    )
    return reducer.fit_transform(query_embeddings)

# IMPORTANT: Use higher-dimensional UMAP (10D) for HDBSCAN input
# The 2D projection is for visualization only — 2D loses information
# HDBSCAN should cluster in 10D space, then project to 2D for display
def project_for_clustering(query_embeddings: np.ndarray) -> np.ndarray:
    reducer_10d = umap.UMAP(n_components=10, n_neighbors=15, metric="cosine", random_state=42)
    return reducer_10d.fit_transform(query_embeddings)
Common mistake to avoid

Do NOT run HDBSCAN on the 2D UMAP projection. The 2D projection optimizes for visual clarity, not cluster preservation — it distorts distances. Always cluster in a higher-dimensional space (10D UMAP or the original embedding space), then project to 2D only for visualization. This is a mistake many implementations make and it produces meaningless clusters.

HDBSCAN configuration

import hdbscan

def identify_clusters(embeddings_10d: np.ndarray) -> np.ndarray:
    clusterer = hdbscan.HDBSCAN(
        min_cluster_size=20,    # minimum 20 queries to form a topic cluster
        min_samples=5,          # core point density threshold
        metric="euclidean",     # Euclidean on UMAP output (cosine handled by UMAP)
        cluster_selection_method="eom",  # excess of mass — better for variable density
        prediction_data=True,   # enables soft clustering for borderline points
    )
    cluster_labels = clusterer.fit_predict(embeddings_10d)
    # cluster_labels[i] = -1 means query i is a noise point (genuine dark zone)
    # cluster_labels[i] >= 0 means query i belongs to cluster label[i]
    return cluster_labels, clusterer

# Cluster naming: use top-5 most representative queries per cluster
def name_cluster(cluster_queries: List[str], cluster_embeddings: np.ndarray) -> str:
    centroid = cluster_embeddings.mean(axis=0)
    similarities = [cosine_similarity([centroid], [e])[0][0] for e in cluster_embeddings]
    representative_queries = [cluster_queries[i] for i in np.argsort(similarities)[-3:]]
    naming_prompt = f"Name this topic cluster in 3-5 words: {representative_queries}"
    return claude_haiku.invoke(naming_prompt)
06

Dark zone classification

Each cluster receives a cluster-level coverage score (mean of all probe coverage scores within the cluster) and is classified into one of three tiers.

Dark Zone
Mean CS < 0.30
Zero or near-zero coverage. Any user query about this topic will likely hallucinate. Highest priority to fix.
Thin Zone
Mean CS 0.30–0.60
Partial coverage. Simple queries succeed, complex ones fail. Adding 2–3 documents would likely fix.
Adequate Zone
Mean CS > 0.60
Good coverage. Not guaranteed perfect but not a priority concern.

Noise points — genuine dark zones

HDBSCAN labels some queries as noise points (cluster = -1). These are not random noise — they are isolated queries with no semantic neighbors in the probe set. In coverage mapping terms, these represent unique topics that didn't cluster with any others: the system has never seen anything like them, and there's probably nothing in the KB related to them either. Noise points should be treated as Dark Zone severity.

Cluster-level coverage computation

def compute_cluster_coverage(cluster_labels, coverage_scores) -> List[ClusterCoverage]:
    results = []
    for cluster_id in set(cluster_labels):
        mask = cluster_labels == cluster_id
        cluster_scores = [coverage_scores[i] for i, m in enumerate(mask) if m]
        mean_cs = np.mean(cluster_scores)
        std_cs = np.std(cluster_scores)
        zone = ("DARK" if mean_cs < 0.30 else
                "THIN" if mean_cs < 0.60 else "ADEQUATE")
        # Severity score: combines mean_cs with cluster size and std
        # Large dark zones with low variance are the highest priority
        severity = (1 - mean_cs) * np.log1p(len(cluster_scores)) * (1 - std_cs)
        results.append(ClusterCoverage(
            cluster_id=cluster_id,
            zone=zone, mean_cs=mean_cs, std_cs=std_cs,
            query_count=len(cluster_scores), severity=severity
        ))
    return sorted(results, key=lambda x: -x.severity)
Cluster Severity Score
Severity = (1 − mean_CS) × log(1 + cluster_size) × (1 − std_CS)

Large dark zones with consistent (low std) failure score highest.
A cluster of 500 queries all scoring CS=0.1 is more urgent than a
cluster of 10 queries averaging CS=0.05.
07

Document recommendation engine

For every Dark or Thin zone cluster, the Cartographer produces a ranked list of documents that would fill the gap. The recommendation engine has three strategies depending on whether the system has access to external data sources.

Strategy A: KB-internal rebalancing

First check if documents already in the KB are being underutilized. Sometimes a topic has coverage but the chunking strategy buried it — long documents where the relevant section is far from the chunk boundaries. For Dark zones, check if any unchunked or poorly-chunked documents cover the topic before recommending external documents.

Strategy B: External document recommendation via web search

async def recommend_documents_for_gap(cluster: ClusterCoverage, cluster_queries: List[str]) -> List[DocumentRec]:
    # 1. Generate a "centroid query" — the most representative query for this cluster
    centroid_query = get_centroid_query(cluster_queries)

    # 2. Generate document search terms from centroid query
    search_terms_prompt = f"""
This is a knowledge gap in a RAG system. Users are asking questions like:
{centroid_query}

Generate 5 specific search queries that would find documents to fill this gap.
Focus on authoritative sources: official docs, academic papers, industry reports.
Return only the search queries, one per line.
"""
    search_queries = await claude_haiku.ainvoke(search_terms_prompt)

    # 3. Web search for each query (using Brave Search API or SerpAPI)
    candidate_docs = []
    for sq in search_queries.strip().split("\n"):
        results = await web_search_api.search(sq, num_results=5)
        candidate_docs.extend(results)

    # 4. Rank candidates by semantic similarity to cluster centroid
    centroid_emb = embed(centroid_query)
    ranked = sorted(
        candidate_docs,
        key=lambda d: cosine_similarity([centroid_emb], [embed(d.title + d.snippet)])[0][0],
        reverse=True
    )
    return ranked[:5]  # top 5 recommendations per gap

Visualization layer

The coverage map is the signature output of the Cartographer — a 2D scatter plot where every dot is a probe query, colored by coverage score, with cluster regions labeled. Dark zones appear as visible red clusters. The map makes the abstract concept of "coverage gap" immediately legible to non-technical stakeholders.

import plotly.express as px
import plotly.graph_objects as go
import dash
from dash import dcc, html

def build_coverage_map(probe_results: List[ProbeResult], clusters: List[ClusterCoverage]) -> go.Figure:
    df = pd.DataFrame([{
        "x": p.umap_x, "y": p.umap_y,
        "coverage_score": p.coverage_score,
        "query": p.query_text,
        "cluster_name": get_cluster_name(p.cluster_id, clusters),
        "zone": get_zone(p.cluster_id, clusters)
    } for p in probe_results])

    fig = px.scatter(
        df, x="x", y="y",
        color="coverage_score",
        color_continuous_scale="RdYlGn",  # red=dark, green=adequate
        range_color=[0, 1],
        hover_data=["query", "cluster_name", "coverage_score"],
        title="Knowledge Base Coverage Map"
    )

    # Add cluster centroid labels for dark and thin zones only
    for cluster in clusters:
        if cluster.zone in ["DARK", "THIN"]:
            fig.add_annotation(
                x=cluster.centroid_x, y=cluster.centroid_y,
                text=f"⚠ {cluster.name}",
                font=dict(size=10, color="red" if cluster.zone=="DARK" else "orange"),
                showarrow=False, bgcolor="white", bordercolor="red"
            )
    return fig

Evaluating the Cartographer itself

The meta-evaluation problem

How do you know if the Cartographer is finding real coverage gaps vs generating false alarms? This requires a held-out validation set of known gaps and known adequate zones — created by deliberately withholding documents from the KB, running the Cartographer, and checking whether the withheld topics appear as dark zones.

Validation methodology: deliberate gap injection

def evaluate_cartographer_accuracy(full_kb: List[Document], cartographer: Cartographer):
    # 1. Select 10 topic clusters from full KB as ground truth
    # 5 will become "injected gaps" (removed), 5 will remain
    topic_clusters = cluster_kb_topics(full_kb, n_clusters=10)
    gap_topics = topic_clusters[:5]      # these become gaps
    control_topics = topic_clusters[5:]  # these remain

    # 2. Create reduced KB with gap topics removed
    gap_doc_ids = {d.id for cluster in gap_topics for d in cluster.documents}
    reduced_kb = [d for d in full_kb if d.id not in gap_doc_ids]

    # 3. Run Cartographer on reduced KB
    report = cartographer.audit(reduced_kb)

    # 4. Check: do gap topics appear as dark zones?
    detected_gap_names = {c.name for c in report.dark_zones}
    true_gap_names = {cluster.topic_name for cluster in gap_topics}
    control_names = {cluster.topic_name for cluster in control_topics}

    precision = len(detected_gap_names & true_gap_names) / len(detected_gap_names)
    recall = len(detected_gap_names & true_gap_names) / len(true_gap_names)
    false_positive_rate = len(detected_gap_names & control_names) / len(control_names)
    return {"precision": precision, "recall": recall, "fpr": false_positive_rate}

RAG system integration

The Cartographer integrates with any RAG system through a simple connector interface. Three connector implementations are provided out of the box.

from abc import ABC, abstractmethod

class RAGConnector(ABC):
    @abstractmethod
    async def query(self, question: str) -> RAGResponse:
        """Submit a query and get retrieved chunks + generated answer."""
        ...

class QdrantRAGConnector(RAGConnector):
    def __init__(self, qdrant_url: str, collection: str, llm_endpoint: str): ...
    async def query(self, question: str) -> RAGResponse:
        chunks = await self._retrieve(question)
        answer = await self._generate(question, chunks)
        return RAGResponse(question=question, chunks=chunks, answer=answer)

class HTTPRAGConnector(RAGConnector):
    """Generic HTTP connector — works with any RAG system that exposes a REST API."""
    def __init__(self, endpoint_url: str, auth_header: str = None): ...
    async def query(self, question: str) -> RAGResponse:
        resp = await httpx.post(self.endpoint_url, json={"query": question})
        return RAGResponse.from_dict(resp.json())

class LangChainRAGConnector(RAGConnector):
    """Wraps any LangChain RetrievalQA chain."""
    def __init__(self, chain): self.chain = chain
    async def query(self, question: str) -> RAGResponse:
        result = await self.chain.ainvoke({"query": question})
        return RAGResponse(question=question, chunks=result["source_documents"], answer=result["result"])

Continuous monitoring mode

Beyond one-time audits, the Cartographer can run in continuous monitoring mode: an Airflow DAG runs a 500-probe mini-audit nightly, tracks the overall_coverage_score trend, and alerts when the score drops by more than 0.05 compared to the previous week — indicating that a KB update introduced new gaps.

Research contributions

Coverage Score formula (CS)

The composite CS — combining Retrieval Confidence, Semantic Entropy, and cross-encoder Hallucination Probability with tunable weights — is a formally defined, novel metric for RAG coverage assessment. The empirical weight calibration on the gap injection benchmark is publishable at ACL System Demonstrations or EMNLP.

The four-strategy probe generation framework

Combining taxonomy-guided, HyDE adversarial, counterfactual, and user-pattern probe generation strategies is a systematic framework for coverage exploration that goes beyond any single-strategy approach in the literature. The characterization of which strategies find which gap types (absolute vs. boundary vs. reasoning) is an empirical contribution.

Gap injection validation methodology

The deliberate gap injection benchmark — withholding KB document clusters and measuring Cartographer detection precision/recall — is a reusable evaluation methodology for any coverage mapping tool. Releasing this methodology enables the community to comparably evaluate future tools.

Severity score for prioritized remediation

The cluster severity score — combining mean coverage, log-cluster size, and coverage consistency — provides a principled prioritization of remediation effort. This is a practical contribution to the emerging field of knowledge base management for production AI systems.
