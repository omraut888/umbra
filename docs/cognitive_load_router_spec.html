Technical Specification · v1.0

Cognitive Load Router

Self-learning LLM gateway that classifies task complexity in under 100ms, routes each call to the optimal model tier, and continuously improves its routing accuracy from production feedback.

XGBoost classifier FastAPI gateway MLflow versioning Online learning Grafana cost dashboard
01

Thesis & problem

Every company building on LLMs routes every call to one model. Usually the most capable one they can afford — because nobody wants to be responsible for the day a cheap model gave a wrong answer on an important query. The result: 70–80% of production LLM spend is wasted routing simple queries to expensive models.

Core insight

Task complexity is predictable before inference. A query like "summarize this sentence" requires fundamentally different reasoning than "given the following SEC filing, calculate the 3-year CAGR of free cash flow and explain whether the trend is consistent with management's guidance." The cognitive load of the second query is 50× the first — and measurable from the query itself, in milliseconds, before spending a single token on inference.

The four cognitive dimensions

Complexity is not one-dimensional. A query can be long but simple (summarize 5 pages of boilerplate). A query can be short but deeply complex (prove the Riemann hypothesis). The router models complexity across four independent axes:

DimensionWhat it measuresProxy signal
Reasoning depthHow many inferential steps are required?Causal connectives, conditional structures, "given that... what if..."
Knowledge breadthHow many distinct domains must be synthesized?Named entity count, domain classifier output, cross-domain term co-occurrence
Instruction precisionHow many constraints must be satisfied simultaneously?Constraint keyword count, format requirements, length specifications
Tool dependencyDoes answering require external tool calls?Query pattern matching, entity types that imply lookup (dates, prices, names)
The key non-obvious insight

Token count alone is a terrible complexity proxy. "Write me a 2000-word summary of this document" has high token output but low reasoning complexity. "What is 2+2?" has minimal tokens but trivially low complexity. The router ignores token count as a primary feature and instead models the reasoning structure of the query.

Key features in detail

Reasoning depth score

import re
import spacy

CAUSAL_CONNECTIVES = ["because","therefore","consequently","as a result","hence","thus","since"]
CONDITIONAL_PATTERNS = [r"\bif\b.{0,50}\bthen\b", r"\bgiven that\b", r"\bassuming\b", r"\bwhat would happen if\b"]
MULTI_HOP_SIGNALS = ["first.*then.*finally", "step by step", "walk me through", "explain how"]

def extract_reasoning_features(query: str) -> dict:
    q_lower = query.lower()
    causal_count = sum(1 for c in CAUSAL_CONNECTIVES if c in q_lower)
    conditional_count = sum(1 for p in CONDITIONAL_PATTERNS if re.search(p, q_lower))
    multi_hop = int(any(re.search(p, q_lower) for p in MULTI_HOP_SIGNALS))
    # Dependency parse for negation depth
    doc = nlp(query)
    negation_depth = sum(1 for token in doc if token.dep_ == "neg")
    return {
        "causal_connective_count": causal_count,
        "conditional_structure_count": conditional_count,
        "multi_hop_indicator": multi_hop,
        "negation_depth": negation_depth,
    }

Domain entropy — measuring cross-domain breadth

from scipy.stats import entropy
import numpy as np

# FastText domain classifier: outputs probability distribution over 10 domains
# Domains: finance, legal, medical, technical, science, history, general, code, math, creative

def compute_domain_entropy(query: str) -> float:
    domain_probs = fasttext_classifier.predict_proba(query)  # shape: (10,)
    # High entropy = query spans multiple domains = more complex routing
    # entropy([1,0,0,...]) = 0 (single domain, simple)
    # entropy([0.1,0.1,...]) = 2.3 (uniform across 10 domains, complex)
    return float(entropy(domain_probs + 1e-10))  # add epsilon for numerical stability
Why domain entropy is powerful

A query about "the tax implications of RSU vesting for employees in California" spans finance, legal, and geographic domains simultaneously — high entropy, high complexity. A query like "what is the capital of France?" is single-domain with near-zero entropy — trivial routing to Tier 0. Domain entropy captures cross-domain complexity that keyword counting misses entirely.

04

Complexity classifier

XGBoost is chosen deliberately over neural models. The gateway is a latency-critical path — classifier inference must complete in under 5ms to keep total routing overhead under 100ms. XGBoost at 28 features runs in ~0.3ms. BERT would add 200ms — defeating the purpose.

Model architecture

import xgboost as xgb
from sklearn.model_selection import StratifiedKFold
import mlflow

class ComplexityClassifier:
    def __init__(self):
        self.model = xgb.XGBClassifier(
            n_estimators=200,
            max_depth=6,
            learning_rate=0.1,
            subsample=0.8,
            colsample_bytree=0.8,
            use_label_encoder=False,
            eval_metric="mlogloss",
            n_jobs=-1,
            tree_method="hist",  # fastest for CPU inference
            num_class=4            # SIMPLE, MODERATE, COMPLEX, EXPERT
        )
        self.feature_extractor = FeatureExtractor()
        self.version = None

    def predict_with_confidence(self, query: str, context: str = "") -> RoutingDecision:
        features = self.feature_extractor.extract(query, context)
        proba = self.model.predict_proba([features])[0]
        tier = int(proba.argmax())
        confidence = float(proba.max())
        # Apply confidence threshold: low-confidence predictions escalate one tier
        if confidence < 0.65 and tier < 3:
            tier += 1  # conservative escalation on uncertainty
        return RoutingDecision(tier=tier, confidence=confidence, feature_vector=features)

Training data bootstrapping

Cold start is the hardest problem. No labeled data exists on day one. The solution is a three-phase bootstrap:

  1. Phase 1 — Rule-based labels (Week 1): Write a deterministic labeling function using the most reliable heuristics (code_generation_flag → Tier 2, query_token_count < 20 AND domain_entropy < 0.5 → Tier 0). Generate 2,000 labeled examples from a diverse query dataset. This is your initial training set. Low accuracy (~65%) but enough to start.
  2. Phase 2 — Human spot-check labels (Week 2): Route 200 queries through all four tiers simultaneously, have a human rate quality per tier, label the minimum tier that achieved "acceptable" quality. Add these 200 to training data. Accuracy improves to ~78%.
  3. Phase 3 — Automated judge labels (Week 3+): The feedback loop (Section 06) generates continuous labels from production. Weekly retraining on the accumulated labeled set. Accuracy reaches 85%+ after ~1,000 production examples.

Calibration

Raw XGBoost probabilities are not well-calibrated — the model is overconfident. Apply Platt scaling (logistic regression on held-out set) to calibrate probabilities. Calibrated confidence scores are used for the escalation logic above — uncalibrated scores would produce too many or too few escalations.

from sklearn.calibration import CalibratedClassifierCV

Cost-quality Pareto frontier

The routing thresholds are not fixed — they are tunable parameters that define a point on the cost-quality Pareto frontier. A COST_WEIGHT parameter (0.0 to 1.0) adjusts whether the system optimizes primarily for cost or quality:

Effective tier threshold with cost weight
effective_threshold(tier) = base_threshold(tier) + COST_WEIGHT × tier_cost_penalty(tier)
where COST_WEIGHT=0.0 → always route to highest-confidence tier
COST_WEIGHT=1.0 → always route to cheapest tier with confidence > 0.50

The Grafana dashboard exposes COST_WEIGHT as a live knob — engineering managers can tune the cost-quality tradeoff without a code deploy.

06

Feedback loop (the learning mechanism)

Why this makes it AutoML, not just a gateway

Without the feedback loop this is a rule-based router. With it, the router continuously learns which feature patterns correspond to quality degradation at lower tiers — and adjusts its routing thresholds accordingly. After 90 days in production, the classifier has learned the specific complexity patterns of your application's queries, making it far more accurate than any pre-trained model.

Quality signal collection (three sources)

Source 1: Judge model (automated, async)

async def judge_response_quality(query: str, response: str, routing_tier: int) -> float:
    # Runs asynchronously after response is returned — zero latency impact
    judge_prompt = f"""
Rate the quality of this AI response on a scale of 0-10.
Query: {query}
Response: {response}

Criteria:
- Accuracy: Does the response correctly answer what was asked?
- Completeness: Does it address all parts of the query?
- Reasoning quality: Are claims supported with logic or evidence?

Return ONLY a JSON: {{"score": N, "issues": ["list of issues if any"]}}
"""
    result = await claude_haiku.ainvoke(judge_prompt)
    return result["score"] / 10.0  # normalize to [0,1]

Source 2: Behavioral signals (implicit)

User behavior reveals quality without explicit feedback:

  • Follow-up clarification: if the next query is "can you clarify..." or "that's not what I meant..." → quality=0.3
  • Immediate retry: same query within 30 seconds → quality=0.2
  • No follow-up: query answered, conversation ends → quality=0.8 (weak positive signal)
  • Explicit thumbs up/down: quality=1.0 or 0.0

Source 3: Counterfactual sampling (weekly)

Weekly, randomly route 2% of queries through all four tiers simultaneously (in shadow mode — the user sees only the routed tier's response). Compare quality scores across tiers for the same query. This directly measures: "was routing this query to Tier 1 as good as Tier 2?" and updates the training labels accordingly.

Retraining pipeline

# Weekly Airflow DAG: retrain_router
def weekly_retrain():
    # 1. Pull feedback records from PostgreSQL
    records = fetch_feedback_records(days_back=7)  # ~10k-50k records

    # 2. Construct training labels
    # Label = minimum tier that achieved quality_score >= QUALITY_THRESHOLD (0.75)
    labeled = []
    for r in records:
        min_acceptable_tier = min(
            tier for tier, score in r.tier_quality_pairs
            if score >= QUALITY_THRESHOLD
        )
        labeled.append((r.feature_vector, min_acceptable_tier))

    # 3. Retrain with accumulated dataset (new + historical)
    X, y = zip(*labeled)
    new_model = ComplexityClassifier()
    new_model.fit(X, y)

    # 4. Evaluate against hold-out set
    accuracy, cost_savings = evaluate_model(new_model, holdout_set)

    # 5. A/B test: route 10% to new model for 24hrs before full deploy

Gateway architecture

FastAPI middleware design

from fastapi import FastAPI, Request, Response
from fastapi.middleware.base import BaseHTTPMiddleware
import time

class RouterMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next) -> Response:
        start = time.perf_counter()

        # 1. Parse request
        body = await request.json()
        query = body.get("messages", [{}])[-1].get("content", "")
        context = body.get("system", "")

        # 2. Check cache (Redis) — identical queries return cached response
        cache_key = f"response:{sha256(query)}"
        cached = await redis.get(cache_key)
        if cached:
            record_cache_hit(query)
            return JSONResponse(json.loads(cached))

        # 3. Route — feature extraction + classification
        decision = classifier.predict_with_confidence(query, context)
        target_model = TIER_TO_MODEL[decision.tier]

        # 4. Rewrite request to target model endpoint
        body["model"] = target_model
        request._body = json.dumps(body).encode()

        # 5. Execute request
        response = await call_next(request)
        routing_ms = int((time.perf_counter() - start) * 1000)

        # 6. Log + async quality judge (non-blocking)
        asyncio.create_task(log_and_judge(query, response, decision, routing_ms))

        return response

Circuit breaker for model tiers

If a model tier starts returning errors (5xx, timeouts), the circuit breaker escalates to the next tier automatically. This prevents a Groq outage from cascading into user-facing failures.

from circuitbreaker import circuit

@circuit(failure_threshold=5, recovery_timeout=30, expected_exception=APIError)
async def call_tier_0(body): return await groq_client.invoke(body)

@circuit(failure_threshold=3, recovery_timeout=60, expected_exception=APIError)
async def call_tier_1(body): return await haiku_client.invoke(body)

async def route_with_fallback(body, tier):
    callers = [call_tier_0, call_tier_1, call_tier_2, call_tier_3]
    for t in range(tier, 4):
        try:
            return await callers[t](body), t
        except CircuitBreakerOpen:
            continue  # escalate to next tier
    raise AllTiersUnavailableError()

-- Materialized view: daily cost savings report
CREATE MATERIALIZED VIEW daily_savings AS
SELECT
    date,
    SUM(cost_usd) AS actual_cost,
    SUM(input_tokens * 0.015 / 1000 + output_tokens * 0.075 / 1000) AS opus_cost_baseline,
    1 - SUM(cost_usd) / SUM(input_tokens * 0.015/1000 + output_tokens * 0.075/1000) AS savings_pct
FROM routing_log
GROUP BY date;

Classifier drift detection

The feature distribution of production queries shifts over time as users' needs evolve. Detect this using Population Stability Index (PSI) — a metric used in credit risk modeling to detect covariate shift:

Population Stability Index (PSI)
PSI = Σ (Actual% - Expected%) × ln(Actual% / Expected%)
PSI < 0.1 → stable (no retraining needed)
PSI 0.1–0.2 → minor shift (monitor)
PSI > 0.2 → significant shift → trigger immediate retraining

Compute PSI weekly over the top-5 most important features. A PSI spike means the classifier was trained on a different query distribution than it's now seeing — its accuracy estimates are unreliable.

Research contributions

The 4-dimensional complexity model

Decomposing query complexity into reasoning depth, knowledge breadth, instruction precision, and tool dependency — with empirically validated feature proxies for each — is a formal contribution to the LLM routing literature. Publishable as a short paper at EMNLP or ACL System Demonstrations.

Online learning router benchmark

The counterfactual sampling methodology (running 2% of queries through all tiers in shadow mode) generates a continuous routing accuracy benchmark that other teams can replicate. Releasing this benchmark enables the research community to evaluate routing systems comparably.

PSI for LLM query drift

Applying Population Stability Index — a concept from credit risk modeling — to detect distributional shift in LLM query patterns is a novel cross-domain application. The PSI thresholds calibrated for LLM routing retraining triggers are a practical contribution.
